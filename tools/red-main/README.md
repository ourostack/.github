# red-main

- `red-main.mjs`: red-minutes measure and owner routing. `owners.json` maps each repository to the coordinator that owns it, and optionally to `fixers`, such as its issue drain: a red main wakes the fixers first, telling them to clear it before other work, then the owner.
- `auto-revert.mjs`: finds the pull request that turned main's ci red and reverts it (design, guards and options in the file header, opt-in list in `auto-revert.json`, tests in `auto-revert.test.mjs`). Below, [How auto-revert finds the culprit](#how-auto-revert-finds-the-culprit).

The measure reads the whole window, not just the API's newest 1,000 runs: it queries `created` ranges and halves any range that reports more than 1,000.

## API budget

Every GitHub API call counts against the repository's hourly allowance, so both tools print what they spent.

- **auto-revert** reads main's push runs newest first (one page of 50 per counted workflow, more only until each has a green run), so a green main costs 1 call (2 with `--apply`, which also lists open pull requests to land its own reverts), plus 1 for each run still going on a commit newer than the newest green, whose jobs are read to see if one already failed. Once red, it reads the failed jobs of the red runs it walks back through (jobs list, each failed job's log, streamed, and annotations only for a job with no failing test), and nothing else from the API: commits, files and imports come from git. `--cache <file>` keeps each finished job's parsed failures, each completed run's jobs list (keyed by run id and attempt, only when every job is completed) and each failed job's annotations, so a later tick reads only what is new: runs lists, running runs' jobs and new logs. A culprit about to be reverted, or its open revert about to merge, also reads up to 3 newer main runs' jobs and, for a test, the passing job's log (kept in `--cache` too), and its cause check's runs at two commits: 2 calls a tick, and the logs of the runs that failed. The run ends with `auto-revert: N API calls (R read, W write)`.
- **red-main** reads a UTC day at a time and keeps finished days (all runs completed) in a cache file (`--cache <file>`, default `~/.cache/red-main.json` or `$RED_MAIN_CACHE`, `--no-cache` to read everything). A repeat run fetches only days not yet cached plus today, today's run-list pages with `If-None-Match` (a 304 is free), and remembers each failed run's infra verdict. Today's pages use the day's fixed range, so their URL (and ETag) is the same on every run. A failure on a commit that comes while a red stretch is already open is not read for infra (it cannot open or close a stretch), so a long red costs the reads of its first commit only. Measured cold on the same 7 days for ourostack/desk: 328 calls before, 190 after; a repeat run reads only today's pages (free when unchanged). It reads `X-RateLimit-Remaining` from every response and, once fewer than 500 calls are left (`RED_MAIN_FLOOR`), stops and prints `PARTIAL`: the repos it did not cover and when the budget resets. The cache keeps what was read, so the next run continues. It prints `red-main: N API calls (M answered 304, free)` to stderr. Persist the file between runs (an Actions cache keyed on the file, or the host's disk).

## Red, waiting for runners, and where a red stretch ends

A red stretch opens at the first failing commit's failure and ends at the **push time** (its first run's start) of the first later commit whose push runs all finished with none failed. The time from that push to its last run finishing is not red: the code was fixed when it landed and the runners were queued. It is reported in its own column, `waiting for runners` (with `% wait`), beside `% red`, so neither hides the other. A wait never overlaps the next red stretch. A fix commit that fails, or is still running, does not end the stretch. Auto-revert judges red differently: by the newest completed run's verdict, not by a stretch of commits ([How auto-revert finds the culprit](#how-auto-revert-finds-the-culprit)).

## Infrastructure failures: `title=infra`

A failed job that is not the code's fault says so with one line. red-main then counts it in the `infra` column, apart from code red: it opens no red episode, wakes no owner, and `auto-revert.mjs` never reverts it. Emit it from the failing step (GitHub turns the workflow command into a check-run annotation titled `infra`):

```
::error title=infra::<reason>
```

Shell step:

```yaml
- run: |
    if ! ./provision-runner.sh; then
      echo "::error title=infra::runner pool exhausted"
      exit 1
    fi
```

Node script (stdout of a step):

```js
console.log("::error title=infra::device farm unreachable");
process.exit(1);
```

Only a job that fails counts; emit it only for causes outside the code under test. A commit that has any non-infra failure is still red. A runner that is lost cannot annotate its own job, so red-main classes these as infra itself, in both `red-main.mjs` and `auto-revert.mjs`: run conclusion `startup_failure`; a run `cancelled` with no newer push of the same workflow (a concurrency cancel by a newer push is not a failure at all; a user's cancel leaves no trace in the API, so it is treated as infra too); a failed job that ran no steps or was assigned no runner; and log or annotation text such as `The runner has received a shutdown signal`, `lost communication with the server`, `The job was not acquired by Runner`, `The operation was canceled`. A run whose only failures show GitHub 5xx (`POST /graphql: 504`, `502 Bad Gateway`) or `ETIMEDOUT` in the job log is classed infra without any annotation.

GitHub's own transient failures (GraphQL "Something went wrong while executing your query", HTTP 502/503/504, secondary rate limits) are retried once after a pause by `tools/infra/infra.mjs`, used by pr-clock, rearm-merges and brand converge; a second failure exits with `::error title=infra::` and the GitHub request id.

**A flake never holds main red, and a re-run is never the verdict.** The first time a push run (attempt 1) is red with a failure not yet confirmed, auto-revert re-runs its failed jobs once (needs actions write: a repository's own caller has it with its `GITHUB_TOKEN`; the central PAT gets a 403, which is logged and skipped). A flake turns green within minutes; a break stays red and the 60-minute wait before any revert still applies. A re-attempt goes back to pending in main's shared concurrency group and may be replaced by the next push, losing its verdict (Tandem, 2026-11-19 01:35Z), and a release waits for a completed green main run, so the verdict also comes from a separate run: auto-revert dispatches the workflow (`workflow_dispatch`, its own group) on a throwaway branch `auto-revert/verify-<sha>` at the red run's commit. A failure that fails there again, or in two main runs in a row, is confirmed; one that passes there is a flake and is never reverted. A culprit is reverted only for a failure that itself reproduced: when the failures that did are dropped as main's own (step 5), one left with only failures that passed there is declined as a flake, never reverted (Tandem's #7976 reverted #7963 for a WebKit test that had passed at the same commit). Each declined failure is a line in the run's summary (`declined revert, a flake to fix: …`), and, with `"flakeIssue": { "title", "labels" }` in the repository's `auto-revert.json` row, a line in one open issue with that title (opened with `ISSUE_TOKEN` when none is, its body added to after, never a comment per tick), so the test's owner fixes the flake. The branch is deleted once main no longer needs it. A main run someone else re-attempted keeps its earlier attempt's failed jobs as its verdict. A repository whose releases pin a main run's first attempt (Tandem) sets `"rerun": false` in its `auto-revert.json` row: its main runs are never re-run, and the verify branch alone tells a flake from a break.

## How auto-revert finds the culprit

A main whose runs share one concurrency group (a waiting run is replaced by the newest commit's) gets a verdict on some commits only, so one red run covers every commit since the run before it. auto-revert never judges the tip, which is nearly always still running when merges come every few minutes.

1. **Red is a verdict.** Each counted workflow (`"workflows"` in `auto-revert.json`, or every push workflow but `"ignoreWorkflows"`) is judged by its newest completed push run on main, newest by commit order (main's first parent, read from the clone once main looks red; run number before that), never by finish time: where each push has a run of its own, an older commit's run can finish after a newer one's, and then says nothing. Pending runs, runs replaced by concurrency and infrastructure-only failures say nothing. A first attempt still running says nothing either, except for a job it has already failed: that job is judged now, its verify run dispatched at once, rather than when the run's slowest unrelated job ends (in a consuming app, a ci run failed its test jobs early and stayed in progress 31 more minutes behind a job that waits on a Mac pass). A job still running says nothing: the run neither fails nor passes a failure in it, so that failure's range and its newest red come from the runs that finished the job, and the run's jobs list isn't cached until it ends. A run cancelled after some of its jobs failed is a red verdict for those jobs, and a run re-attempted by hand keeps its earlier attempt's. A newer completed green run clears it. A workflow in the repository's `"tagRuns"` (also in its `"workflows"`) has no push runs: its main runs are dispatched on the release tag of a commit on main (a consuming app's Mac guards, `mac-guards.yml`, started on each promoted release), so its `workflow_dispatch` runs on a `vX.Y.Z` tag are judged instead, each for its tag's commit, in the same commit order; its verify runs work as for any workflow. A workflow in the repository's `"bisectRuns"` (also in its `"workflows"`) runs on some of main's commits only, in a shared concurrency group, and bisects a red range itself: it dispatches itself (`workflow_dispatch`) on a branch `auto-revert/bisect-<sha>` at a commit inside the range. Those runs are read beside its push runs and judge their commits in commit order, never by run number (a green one at an older commit never clears main), so the range in step 3 narrows to the one commit that broke it.
2. **Failures.** The red run's failed jobs are read from their logs: each failing node:test (`not ok`, with its `location:` file and every repository file its failure text names), each case a known-failing list's judge fails (`<engine> failed <file>:<case>, which <list> doesn't list: …`, Tandem's WebKit burst), or, for a job with no failing test, the job, the files its error lines name and the files its failing step's `run:` names in the workflow file at that commit (the script it runs), with a reusable workflow's job (`stage / build-and-sign`) read from the file its caller's job uses. The local actions (`uses: ./<dir>`) its earlier steps ran are kept as the job's setup.
3. **Range.** Each failure is followed back through the older completed runs to the newest one where it didn't fail. It began in a commit after that run, up to the first run where it failed.
4. **Attribution.** From the failing test file and the files its failure names, the code is followed through runtime imports and the repository paths it names as strings (a spawned script, a fixture), at the commit that first failed; type-only imports don't count. A test (or test helper) also depends on what it reads as text, by the rule Tandem's PR test selection uses (`scripts/affected-tests.ts`, #4096): a repository path anywhere in it (path.join's quoted pieces joined), a file's name in quotes, and a non-module's name anywhere; and a test that scans a directory (`readdirSync` and the like over a path it names) depends on every file added under it. The squash-merged pull request in the range that changed the closest file is the culprit. When several did, the one whose change touches the most code names the failing assertion uses wins (the test line that carries the failure's message, and the failure text); with no such evidence, the newest. A job's failure that no pull request in the range reaches is followed from the job's setup instead (each earlier step's local action changes what every later step runs, such as a shim on the PATH), so a change to it is the culprit even when the failing line looks like the machine's (Tandem's release build failed with "Resource temporarily unavailable (os error 35)" on every run after a gh shim's action was added, and nothing was blamed). Nothing reachable and one pull request in the range: that one. Otherwise the failure is reported, unattributed, and red-main wakes the owner. A pull request already reverted while the failure stayed is passed over, so the next closest is tried.
5. **Guards.** A culprit is skipped while unconfirmed (the verify run at the same commit decides), when that run passed it (a flake), when a commit on main since the red run names it (`main red since #N`, a revert), when every failure it is blamed for is settled on main since (a newer commit changed the failing test or a file the failure names), when a fix or revert pull request for it is open, and while main has been red under the repository's `minRedMinutes` (60 by default; one consuming app's is 0: it acts on confirmation). A failure main already had is never blamed on the range: one that main's runs of the same workflow failed the same way (the same test, or the same job and step) in the 24 hours before the range began (up to 12 red runs read, their logs cached), or whose test the repository's flake table names under a heading "Open known flakes" (its `"knownFlakes"` file in `auto-revert.json`, each item naming the test file in backticks). A pull request that changed the failing test, or a file its failure names, is still blamed. Nor is a failure blamed on a pull request picked only because it was the range's one pull request (nothing it changed reaches the failure) when it changed only existing test files of its own and documents (no product code, test helper or harness, workflow, CI config, package or lock file) and added, removed or renamed no test file, so no shard's files moved. A culprit left with no failure of its own is not reverted; the evidence is posted on its pull request once instead (a consuming app's #5252 reverted #5241, a types-only change, for a test main had failed the same way twice that night). A repository with `"revertOnlyNamed": true` (one consuming app's) has a culprit reverted only when its range is that one pull request (a bisect or a single merge named it), or a failure names a file only it changed in the range (a consuming app's #5789); one picked from several by what it changed gets one issue for its lane instead (a consuming app's #5333 reverted #5289 over Windows failures it didn't cause).
6. **Cause check.** One green proves nothing about a race: a flaky regression passes now and then. So a culprit is reverted by cause when a failure it is blamed for passed in a later main run at a commit that contains it (the same job passed whole and its log shows that test passing: `ok N - <test>`, or, from a known-failing list's judge, the test's file named; a skipped or cancelled job, or a run that didn't run or skipped the test, counts as nothing), or passed when its workflow ran again at the red commit (even if two red runs in a row confirmed it). Its workflow is dispatched at the culprit's parent and at the culprit, `causeRuns` times each (5 by default, in `auto-revert.json`), each run on its own branch `auto-revert/verify-<sha>-cause-<pr>-<i>-<workflow>` (named like a verify branch, so a caller woken by a finished verify run wakes for these too); a row's `repeatInput` names a workflow input that takes the count instead (one run each), and `testInput` one that takes the failing test files. The tick never waits: the runs are found again by commit on later ticks, and none is dispatched twice; a side whose runs are already there isn't dispatched again. Only when the parent passed every run and the culprit failed it at least once is the culprit reverted. When the parent failed it too, it is a race on main; when neither failed, or runs are missing, no cause was found. Either way nothing is reverted, the tool's open revert of it is closed with a comment naming the runs, and the flake issue gets a line naming the test and both commits. The same check runs again before the tool merges its own open revert (each revert's body keeps what it needs in a hidden comment), and turns off its auto-merge while it runs. The reproduction rule (step 5) still comes first. In a consuming app on 2026-11-28, a racy window test failed twice at a commit whose only pull request changed release promotion code, passed on the next commit two minutes after the revert opened, and the revert merged three minutes later.
7. **Revert and land.** Each culprit gets its own revert (GitHub's `revertPullRequest`), so two breaks in one range are both reverted in one cycle. It turns on auto-merge where the repository allows it; on every tick it also merges its own open revert pull requests whose head checks are green (the repository's `.github/merge-checks.json` `required` list when it has one, and never with a failed check), so a revert lands like any pull request and main is green after the next ci run. One exception: when main is red and every failure in the revert's own checks is one main already has now (another pull request's break, or a flake), none of them its own culprit's, it lands once nothing still runs. It adds no red and takes its culprit's out (a consuming app's #4641 waited 33 minutes behind #4640's failure in its own gate).

Replay any moment: `node tools/red-main/auto-revert.mjs --repo <owner/repo> --as-of <ISO time>` judges main as it stood then (runs created later unseen, runs finishing later still running) and only says what it would do. Commits and files come from `--git <clone>`, or a blobless clone of its own (in `$RUNNER_TEMP` or `~/.cache/auto-revert`), which fetches each commit's source files in one request. In Actions, git authenticates through `GIT_CONFIG_*` environment variables, never the command line.

## Opting a repository in with its own token (no cross-repo secret)

Add `.github/workflows/auto-revert.yml` to the repository:

```yaml
name: Auto-revert red main
on:
  schedule:
    - cron: "4-59/10 * * * *"
  workflow_run:
    workflows: [ci]            # your required workflow's name; cron alone can be delayed or dropped
    types: [completed]
    branches: [main]
  workflow_dispatch:
permissions:
  contents: write
  pull-requests: write
  actions: write
  checks: read
jobs:
  auto-revert:
    uses: ourostack/.github/.github/workflows/auto-revert-reusable.yml@main
    secrets:
      token: ${{ secrets.AUTO_REVERT_TOKEN }}   # optional, see below
```

The repository's Actions settings must allow workflows to create pull requests, and the repository must be able to use the public `ourostack/.github` workflow (Settings > Actions > General, for private repositories in other orgs). The workflow reads everything, check runs, `title=infra` annotations and the repository's history (a blobless git clone) included, with the caller's `GITHUB_TOKEN` (so the caller must grant `contents: read`, `checks: read`, `actions: read` and `pull-requests: read`, the last for `commits/{sha}/pulls`, without which a caller that keeps its own read-only permissions fails every run with `Resource not accessible by integration`; a fine-grained `AUTO_REVERT_TOKEN` cannot read Checks), and uses `AUTO_REVERT_TOKEN` only for the writes: revert branch, PR, auto-merge, the merge of its own green revert, and the verify branch and its dispatch (contents and actions write; the workflow must have a `workflow_dispatch` trigger, or two red runs in a row confirm instead). If annotations cannot be read, auto-revert treats the failure as "can't tell" and does not revert. Without the token, `GITHUB_TOKEN` does the writes too (contents, pull-requests and actions write). GitHub does not start `pull_request` workflows for a PR opened with `GITHUB_TOKEN`, so the revert PR's required checks would never report; pass a PAT or GitHub App token as the optional `AUTO_REVERT_TOKEN` secret to avoid that (or run the repository's required checks on `workflow_dispatch`/`push` too). To make auto-revert ignore a workflow whose red says nothing about the commit before it (a gate that checks only the newest commit), add its file name without `.yml` (or its workflow name) to that repository's `"ignoreWorkflows"` list in `auto-revert.json`; its runs are not read, so they neither start nor extend a red stretch. The list applies to caller workflows too (`--self` reads the repository's row), so a caller adds nothing to its own file. A repository that keeps the central PAT for reverts (so its revert PRs start their required checks) can still get the early re-run: its caller passes `with: { rerun-only: true }`, needs only `actions: write` and `contents: read` / `checks: read` / `actions: read`, and never reverts. Add `"enabled": false` rows to `auto-revert.json` only for repositories the central cron should cover.

### teams-microsoft/tandem

1. Add the caller file above as `.github/workflows/auto-revert.yml`.
2. Settings > Actions > General > Workflow permissions: tick "Allow GitHub Actions to create and approve pull requests".
3. Create the `AUTO_REVERT_TOKEN` secret (a token with contents and pull-requests write) so the revert PR's checks run. Without it the revert PR needs its checks started by hand.
4. Dry run first: set `apply: false` through a `with:` block, or `workflow_dispatch` and read the summary; then leave it on.
